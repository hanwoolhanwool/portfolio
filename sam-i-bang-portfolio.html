MediaPipe 입력 브릿지 — 스레드 경계와 제로 할당

파이프라인 02–03
GestureRecognizer/Input/HandLandmarkProvider.cs100%
문제

MediaPipe 추론은 워커 스레드에서 끝나는데 Unity API는 메인 스레드 전용입니다. 게다가 프레임마다 손당 21개 점을 List<List<float>>로 새로 만들면 GC가 계속 튀어 프레임이 끊깁니다.

해결

추론 결과를 ConcurrentQueue에 적재하고 Update()에서 메인 스레드로 펌프하는 브릿지를 두었습니다. 큐에는 상한(30)을 걸어, 메인 스레드가 밀리면 오래된 프레임부터 버립니다. 모션 입력은 정확한 과거보다 최신 상태가 중요하기 때문입니다.

성능

손 데이터 객체는 풀에서 꺼내 쓰고 디스패치 직후 되돌립니다. 내부 리스트를 Clear()만 하고 구조는 재사용해, 프레임당 할당을 사실상 없앴습니다.

경계

이벤트 페이로드를 float·List<float>·bool 같은 순수 타입으로만 노출했습니다. 덕분에 구독 측이 MediaPipe 어셈블리를 참조하지 않아도 되고, 나중에 입력원을 네트워크 전송으로 바꿔도 위 레이어는 그대로입니다.

// (워커 스레드) 추론 결과 적재 — 큐가 차면 가장 오래된 프레임을 버린다
public void ProcessHandResult(HandLandmarkerResult result, int w, int h)
{
    if (_pendingData.Count >= MAX_QUEUE_SIZE)
        _pendingData.TryDequeue(out _);
    _pendingData.Enqueue(packet);
}

// (메인 스레드) 펌프 후 풀로 반환
private void Update()
{
    while (_pendingData.TryDequeue(out var packet))
    {
        OnHandDataReceived?.Invoke(Time.time, _cachedAspectRatio,
                                   packet.leftHand, packet.rightHand);
        ReturnHandDataToPool(packet.leftHand);
        ReturnHandDataToPool(packet.rightHand);
    }
}

구조

개별 제스처는 IHandGesture를 구현한 독립 클래스입니다. 손가락 펴짐 상태를 받아 불리언 패턴 하나로 판정하므로, 제스처 추가는 클래스 하나 추가로 끝나고 인식기·프로세서 코드는 건드리지 않습니다.

성능

가장 비싼 룰 매칭은 새 손 데이터가 올 때만(약 30Hz), 시간 기반 디바운스는 매 프레임(60Hz 이상) 돌립니다. 두 주기를 Evaluate / TickTimers로 분리해 연산량과 반응성을 동시에 잡았습니다.

활 시퀀스

활은 단발 제스처가 아니라 "양손 주먹으로 조준 → 왼손 주먹 + 오른손 펼침으로 발사"의 연속 동작입니다. 별도 상태머신으로 단계·실패·쿨다운을 관리하고, 트래킹이 끊기면 Failed를 거쳐 항상 안전 상태로 수렴시켰습니다.

방어 방향

왼손·오른손·양손 3채널을 독립 평가해 방어 방향을 정하고, 각 방향은 고정된 색 언어를 갖습니다.

정면 방어 · Front Guard Cyan 좌 방어 · Left Guard Jade 우 방어 · Right Guard Violet 
// 제스처 룰 = 손가락 펴짐 패턴 하나. 추가는 클래스 1개로 끝난다
public sealed class ClosedFistGesture : IHandGesture

    public HandGestureType Type => HandGestureType.Closed_Fist;
    public bool Match(Vector3[] lm, Handedness hand, in FingerStates f)

문제

입력이 불안정하다는 전제 자체가 설계 제약이었습니다. 오인식 한 번이 "공격 중인데 방어 상태"처럼 모순된 상태를 만들면 게임이 그대로 망가집니다.

해결

상태를 하나로 뭉치지 않고 이동 · 전투 · 생존 세 축으로 나눴습니다. 축마다 전이 규칙이 독립적이라, 전투 상태가 튀어도 이동·생존은 영향을 받지 않습니다. 피격·무적·이동 잠금은 생존 축에서만 판정합니다.

이동 잠금

보스 벽·포탈 대기·컷신처럼 이동을 막는 이유가 여럿이라, 불리언 하나가 아니라 잠금 사유 집합으로 관리합니다. 사유가 하나라도 남아 있으면 잠금이 유지되므로, 두 시스템이 동시에 잠갔다 한쪽이 풀어도 잠금이 새지 않습니다.

개발 편의

카메라 없이도 QA할 수 있도록 넘패드 입력(방어 8/6/4, 공격 9, 점프 7)과 체력 자동 회복 컴포넌트를 붙였습니다. 웹캠 세팅 없이 레벨 디자인 검증이 가능해졌습니다.

배경

낙타·미어캣·선인장처럼 길목에 배치되는 환경 몬스터는 보스만큼의 AI가 필요 없지만, 플레이어가 다가오면 반응하고 때로는 공격까지 해야 했습니다. 개체마다 전용 스크립트를 붙이면 종류가 늘어날수록 관리가 불가능해집니다.

해결

동작을 세 개의 재사용 컴포넌트로 쪼갰습니다. 트리거 존 진입 시 Animator 파라미터를 발동하는 AnimationTriggerReaction, 그 발동을 구독해 지정 지연 뒤 OverlapBox로 근접 판정을 넣는 AnimationTriggeredAttack, 피격 시 _BaseColor를 잠깐 되돌리는 DamageFlash입니다. 새 몬스터는 컴포넌트 조합과 인스펙터 값만으로 완성됩니다.

문제

AI 생성 모델(Meshy)의 Humanoid 리그는 Idle 상태가 비어 있으면 머슬 기본 포즈로 풀려 몬스터가 웅크린 채 서 있었습니다. 별도 아이들 클립이 없는 모델이 대부분이었습니다.

도구

에디터에서 잡아둔 현재 포즈를 HumanPoseHandler로 읽어 전 머슬 값을 상수 커브로 굽는 IdlePoseBaker를 만들었습니다. 1프레임 클립이 생성되고 Animator의 Idle 상태에 자동 연결됩니다. 걷기·춤 같은 루프 애니메이션 연결도 EnviromentAnimationSetup으로 자동화했는데, FBX 서브에셋의 fileID가 임포트 시점에 결정돼 프리팹 YAML을 손으로 쓸 수 없기 때문입니다.

배경 연출

구름·유적처럼 하늘을 채우는 오브젝트는 CameraRelativeObject로 카메라 기준 상대 배치·이동시켜, 레벨 길이가 바뀌어도 배경을 다시 깔지 않게 했습니다.
