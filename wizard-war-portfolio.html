카메라 시스템 — 전략 패턴 전환

551줄 / 9파일
Camera/MainCamera/InGameCameraManager.cs100%
Camera/MainCamera/FirstPersonCamera.cs100%
Camera/MainCamera/ThirdPersonCamera.cs100%
Camera/FirstPersonCameraController.cs94%
문제

초기 FirstPersonCameraController 하나가 마우스 회전, 사망 시 3인칭 전환, 커서 잠금, 오디오 리스너 등록, 설정값 반영을 모두 떠안고 있었습니다. 사망 → 관전 → 로비 복귀를 반복하면 부모 해제와 회전 초기화 순서가 어긋나 카메라가 허공에 남는 문제가 반복됐습니다.

해결

ICameraMode(Enter/Exit/Tick) 인터페이스를 두고 1인칭·3인칭을 각각 독립 클래스로 분리한 뒤, InGameCameraManager가 Dictionary로 모드를 라우팅하도록 재설계했습니다. 진입·해제 시 필요한 초기화가 각 모드 안에 갇히면서 전환 순서 문제가 구조적으로 사라졌습니다.

디테일

1인칭은 Update, 3인칭은 LateUpdate에서 Tick()을 호출합니다. 추적 대상이 이동을 끝낸 뒤 카메라가 따라가야 3인칭에서 떨림이 생기지 않기 때문입니다.

public void ChangeState(State.CameraState newState)
{
    if (newState == CurrentState) return;

    var prev = CurrentState;
    _currentMode?.Exit();                       // 이전 모드가 자기 뒷정리를 책임진다

    if (_cameras.TryGetValue(newState, out var next))
    {
        _currentMode = next;
        _currentMode.Enter(_player, _playerInput);
        CurrentState = newState;
        OnCameraStateHandler?.Invoke(prev, newState);
    }
}

Photon 룸 진행 관리 — RoomDirector

520줄 / 9파일
Network/RoomDirector.cs56%
Network/PhotonCallBack.cs100%

범위

룸 상태 머신(Waiting/Playing/GameOver), 준비 완료 동기화, 로딩바 갱신, 게임 시작 조건 판정, 마스터 클라이언트 교체 대응, 연결 종료·퇴장 처리, 로비 복귀까지를 담당했습니다.

설계

준비 상태를 RPC가 아니라 룸 CustomProperties에 쌓았습니다. RPC는 보낸 순간 이후 들어온 클라이언트가 받지 못하지만, 프로퍼티는 방에 남아 있어 늦게 접속한 사람도 현재 준비 인원을 그대로 읽을 수 있습니다. 프로퍼티가 갱신될 때마다 OnRoomPropertiesUpdate가 호출되므로 로딩바 갱신 트리거도 같은 채널로 통일했습니다.

안정성

로비 복귀 시 PhotonNetwork.IsMessageQueueRunning을 잠시 꺼서 씬이 바뀌는 동안 도착한 RPC가 이미 파괴된 오브젝트를 건드리지 않게 막았습니다.

// 준비 완료를 룸 프로퍼티에 기록 → 모든 클라이언트가 같은 소스를 읽는다
public void SendReady()
{
    var props = new ExitGames.Client.Photon.Hashtable
    {
        { $"Ready_{PhotonNetwork.LocalPlayer.ActorNumber}", true }
    };
    PhotonNetwork.CurrentRoom.SetCustomProperties(props);
}

// 마스터만 전원 준비 여부를 검사해 시작을 선언
private void CheckGameStartCondition()
{
    if (!PhotonNetwork.IsMasterClient || CurrentState != State.RoomState.Waiting) return;

    foreach (var player in PhotonNetwork.PlayerList)
    {
        string key = $"Ready_{player.ActorNumber}";
        if (!PhotonNetwork.CurrentRoom.CustomProperties.ContainsKey(key) ||
            !(bool)PhotonNetwork.CurrentRoom.CustomProperties[key]) return;
    }
    GameStart();
}

매칭 시스템 — MatchManager

277줄 / 3파일
Network/MatchManager.cs81%
Network/IMatching.cs100%
문제

처음에는 로비 인원과 방 개수의 비율을 계산해 방 생성과 랜덤 참가를 직접 분기했습니다. 두 클라이언트가 같은 순간 "방이 없다"고 판단하면 각자 방을 만들어 1인 방 두 개가 생기는 경합이 발생했습니다.

해결

분기를 없애고 JoinRandomOrCreateRoom 하나로 통일했습니다. "매칭 중인 방이 있으면 참가, 없으면 그 이름으로 생성"을 서버가 원자적으로 판정하므로 클라이언트 간 경합 자체가 사라집니다. 매칭 중인 방만 후보로 잡히도록 CustomRoomPropertiesForLobby에 상태 키를 등록했습니다.

시작 조건

최소 인원(2명)이 모이면 8초 타이머 후 시작, 정원(4명)이 차면 즉시 시작으로 이원화했습니다. 대기 중 방장이 나가면 OnMasterClientSwitched에서 새 방장이 타이머를 이어받아, 남은 사람들이 무한 대기에 빠지지 않습니다.

PhotonNetwork.JoinRandomOrCreateRoom(
    expectedCustomRoomProperties: expectedProps,   // state == Matching 인 방만
    expectedMaxPlayers: 0,
    roomOptions: roomOptions,
    roomName: roomName);                            // 없으면 이 이름으로 생성

구조

Esc 메뉴 · 설정 · 종료 확인 세 화면이 서로를 열고 닫는 관계라, 각 버튼이 상대 UI를 직접 여닫으면 조합이 폭발합니다. InGameEscUI가 세 화면의 상태를 한 곳에서 확정하는 방식으로 정리해, 버튼은 "어떤 화면이 되어야 하는지"만 지시합니다.

입력

Esc는 씬마다 다른 컴포넌트가 아니라 GlobalInputManager가 전역으로 한 번만 구독하고, 게임 상태(로비 / 매칭 / 인게임 / 종료)에 따라 동작을 분기합니다. 게임 종료 화면에서는 아예 무시해, 결과 화면에서 설정이 열리는 문제를 없앴습니다.

연동

설정 창이 열리면 PlayerStateSetting 상태로 전환해 이동·스킬 입력을 차단하고, 감도·카메라 높이는 PlayerData를 통해 실시간 반영 후 PlayerPrefs에 저장합니다.

구현

탑뷰 카메라의 Render Texture를 배경으로 깔고, 월드 좌표를 맵 스케일로 나눠 UI 좌표에 대응시켰습니다. 아이콘은 공통 베이스를 상속한 플레이어 · 트로피 · 포탈 세 종류로 나눠, 각자의 표시 조건만 재정의하도록 했습니다.

밸런스

"생존자가 2명 남으면 트로피와 포탈 위치를 공개한다"는 규칙은 기획 검증 중 자주 바뀌었습니다. 이 조건을 MiniMapSettings(ScriptableObject)로 빼서, 빌드 없이 인스펙터에서 켜고 끄며 테스트할 수 있게 했습니다.

결합도

트로피 스크립트는 다른 팀원 담당이라, 미니맵이 트로피 내부를 직접 참조하는 대신 MiniMapIconManager를 통해 상태 변경 이벤트만 주고받게 연결했습니다.

문제 해결 기록

멀티플레이 QA에서 재현된 버그 중, 원인이 구조에 있었던 사례들입니다. 커밋 해시는 실제 저장소 기록입니다.

설정 창을 닫아도 마우스 커서가 1초간 남는 문제

커서 잠금을 WaitForSeconds(1f) 뒤에 걸고 있었습니다. UI가 닫히는 프레임과 잠금 프레임이 어긋나 그 사이 클릭이 게임 월드로 새어 들어갔습니다. 대기를 WaitForEndOfFrame으로 바꿔, UI 처리가 끝난 바로 그 프레임 끝에 잠기도록 했습니다.

매칭 버튼 연속 클릭 시 방이 중복 생성되는 문제

방장이 로딩 중 나가면 전원이 로딩 화면에 갇히는 문제

게임 시작 조건 검사를 마스터 클라이언트만 돌리는데, 그 마스터가 이탈하면 검사 주체가 사라졌습니다. OnMasterClientSwitched에서 새 마스터가 로딩 코루틴을 다시 시작하도록 해, 승계된 방장이 판정을 이어받습니다.
