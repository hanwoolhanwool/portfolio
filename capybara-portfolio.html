판정 규칙

이 게임의 모든 것이 걸린 한 가지 계산입니다. 노트와 판정선의 가로 겹침 비율로 등급이 갈리고, 등급이 점수 배율을 정합니다. 시간이 아니라 UI 좌표의 겹침으로 판정해, 프레임레이트가 흔들려도 화면에 보이는 것과 판정이 어긋나지 않습니다.

문제

판정 클래스 하나가 겹침 계산, 콤보 갱신, 점수 산출, 파티클 15종 생성, 애니메이터 제어를 전부 들고 있었습니다. 밸런스를 한 번 만지면 연출이 깨지고, 연출을 고치면 점수가 틀어졌습니다.

해결

책임을 넷으로 갈랐습니다. NoteJudge가 겹침을 계산하고, ComboTracker가 콤보 상태를, ScoreCalculator가 점수 산술을 맡습니다. 셋 다 MonoBehaviour가 아닌 순수 클래스입니다. JudgementSystem은 이들을 호출해 흐름만 조율하고, 파티클·애니메이션은 런타임에 붙는 JudgeEffectPresenter에 위임합니다.

호환

연출 프리팹 참조 15개는 씬 와이어링을 깨뜨리지 않으려고 JudgementSystem의 SerializeField에 그대로 두고, 시작 시 프레젠터에 주입했습니다. 리팩터링 때문에 아티스트가 씬을 다시 연결하는 일이 없게 한 선택입니다.

콤보 규칙

콤보는 단순 연속 히트가 아니라 같은 근육 부위를 연달아 쳤을 때만 이어집니다. 부위가 바뀌면 초기화되고, 페이즈가 넘어가면 감소 패널티가 붙습니다.

// 노트 폭 대비 겹침 비율로 등급을 가른다 (씬 의존 없는 순수 계산)
float noteW     = Mathf.Max(0f, noteR - noteL);
float overlapW  = Mathf.Max(0f, Mathf.Min(noteR, pointR) - Mathf.Max(noteL, pointL));
float overlapRatio = (noteW > 0f) ? (overlapW / noteW) : 0f;

if (overlapRatio >= 1f - Epsilon)          // 판정선 안에 완전히 포함
    { accuracy = JudgeAccuracy.Perfect; multiplier = 1.1f; }
else if (overlapRatio >= goodOverlapRatio) // 인스펙터에서 조정 (기본 0.60)
    { accuracy = JudgeAccuracy.Good;    multiplier = 0.8f; }
else
    { accuracy = JudgeAccuracy.Miss;    multiplier = 0f;   }

구조

게임은 6개 상태(Intro · Start · Playing · Rest · End)를 오갑니다. GameManager가 전이를 단일 진입점에서 처리하고 OnGameStateChanged로 알리면, UI·사운드·노트 스포너가 각자 구독해 반응합니다. 상태를 바꾸는 코드가 UI를 직접 건드리지 않습니다.

난이도

운동 강도는 5단계 페이즈로 올라갑니다. 페이즈마다 휴식 전환 임계 터치 수가 달라(12 → 25) 뒤로 갈수록 오래 버텨야 쉬는 구간이 옵니다.

컨디션

Miss는 컨디션을 깎고 Perfect·Good은 회복시킵니다. 컨디션이 0이 되면 게임 오버라, 정확도가 곧 생존 시간이 됩니다. 값 로직은 ConditionModel이라는 순수 클래스가 갖고, ConditionSystem은 슬라이더 표시와 감소 코루틴만 맡습니다.

휴식

휴식 구간에서는 프로틴을 먹어 컨디션을 조금씩 회복하고, 이때도 콤보 배율(1.2 / 1.3 / 1.4)이 붙어 점수가 쌓입니다. 쉬는 시간이 그냥 멈춤이 되지 않게 한 장치입니다.

앱인토스 플랫폼 연동

124줄 / 1파일 + SDK 마이그레이션
Integration/AppInTossBridge.cs100%
Score/ResultSubmitter.cs100%
범위

게임을 토스 미니앱으로 올리기 위해 WebGL 빌드 파이프라인을 구성하고, 공식 apps-in-toss-unity-sdk로 마이그레이션했습니다. 그 과정에서 Unity도 6000.0.31f1에서 6000.3.2f1로 올렸습니다.

리더보드

게임 종료 시 최종 점수를 앱인토스 리더보드에 제출합니다. 제출은 비동기라, 응답을 기다리는 동안 다시 호출되면 중복 제출이 됩니다. isSubmittingScore 플래그로 재진입을 막고 finally에서 반드시 해제해, 예외가 나도 플래그가 잠기지 않게 했습니다.

방어

제출 전에 숫자 형식을 검증하고, 응답은 StatusCode로 분기합니다. 응답이 아예 없는 경우(지원하지 않는 앱 버전)까지 별도 경고로 구분해, 실패 원인을 로그만 보고 판별할 수 있습니다.

if (isSubmittingScore) return;      // 응답 대기 중 재호출 차단
isSubmittingScore = true;
try
{
    var result = await SubmitLeaderboardScoreViaOfficialSdk(score);
    if (result == null)                       // 미지원 앱 버전
        Debug.LogWarning("[AIT] 지원하지 않는 앱 버전이거나 응답이 없습니다.");
    else if (result.StatusCode != "SUCCESS")
        Debug.LogWarning($"[AIT] 점수 제출 실패: {result.StatusCode}");
}
finally { isSubmittingScore = false; }        // 예외에도 반드시 해제

설계

하이퍼캐주얼은 한 판이 짧아서, 다시 켤 이유가 필요했습니다. 결과 화면에서 플레이 방식에 따라 다른 카피바라가 나오고 도감에 수집되도록 만들었습니다.

규칙

기본은 총점 구간으로 Normal 등급을 정하지만, 총점이 6만 이상이고 특정 부위 점수가 나머지 합의 2.5배를 넘으면 Rare로 승격됩니다. "가슴만 판 사람"과 "골고루 한 사람"이 다른 결과를 받는 구조라, 같은 점수라도 플레이 스타일이 결과에 남습니다.

구현

선정 규칙은 CapybaraSelector라는 순수 static 클래스에 두어 스프라이트·저장소와 분리했습니다. 결과는 CapybaraSelection(등급 + 인덱스) 구조체로만 반환하고, 어떤 이미지를 띄울지는 패널 쪽이 결정합니다.

저장

해금 상태는 등급별 키로 UserData에 저장합니다. 잠금(0)·해금(1) 값을 색으로 바꾸는 확장 메서드를 둬서, 도감 패널은 실루엣 처리를 한 줄로 끝냅니다.

// 점수가 충분하고 특정 부위가 압도적이면 Rare로 덮어쓴다
public static CapybaraSelection Select(ScoreResult result)
{
    CapybaraSelection baseSelection = SelectByScore(result.totalScore);

    if (result.totalScore >= RareUnlockScore &&
        TryGetDominantRare(result, out int rareIndex))
        return new CapybaraSelection(CapybaraTier.Rare, rareIndex);

    return baseSelection;
}

문제

리듬 게임은 노트와 판정 파티클을 초당 여러 개 만들고 버립니다. WebGL은 GC가 멈추면 그대로 프레임이 튀기 때문에, Instantiate/Destroy 반복이 가장 큰 위험이었습니다.

풀링

프리팹을 키로 쓰는 제너릭 풀을 만들어 인스턴스를 비활성 상태로 재사용합니다. 씬 전환으로 파괴돼 null이 된 항목은 대여 시 건너뛰고, 반납분은 씬 전환에도 살아남는 비활성 루트에 모읍니다.

이중 반납

연출을 교체할 때 같은 인스턴스가 두 경로에서 반납될 수 있었습니다. 대여 시 세대 토큰을 함께 발급하고 반납 시 세대가 일치할 때만 받아들여, 이미 재사용 중인 오브젝트가 다시 풀에 들어가는 것을 막았습니다.

로깅

디버그 로그를 GameLogger로 감싸고 [Conditional("UNITY_EDITOR")]·[Conditional("DEVELOPMENT_BUILD")]를 걸었습니다. 릴리즈 빌드에서는 호출 자체가 컴파일 단계에서 사라져 문자열 보간 비용까지 함께 없어집니다.

밸런싱

컨디션 증감, 콤보 배율, 페이즈별 휴식 임계치를 전부 GameSettings(ScriptableObject)에 모아 단일 출처로 삼았습니다. 수치 조정에 빌드가 필요 없어, 플레이 테스트 중에도 바로 고칠 수 있습니다.

// 릴리즈 빌드에서는 호출부가 통째로 제거된다 (문자열 보간 비용 포함)
[Conditional("UNITY_EDITOR")]
[Conditional("DEVELOPMENT_BUILD")]
public static void Log(object message) => UnityEngine.Debug.Log(message);

문제 해결 기록

플랫폼 특성상 기기·화면 비율이 제각각이라, 구조에서 원인을 찾아야 했던 사례들입니다.

기기마다 팝업이 화면을 벗어나던 문제

웹뷰 폭이 기준 해상도보다 좁으면 팝업이 잘렸습니다. OnRectTransformDimensionsChange로 캔버스 크기 변화를 감지해, 기준 폭 대비 비율만큼 팝업을 축소하고 가로로 꽉 차야 하는 요소는 폭만 늘리도록 나눴습니다. 축소와 확장을 한 값으로 처리하지 않은 게 핵심이었습니다.

앱인토스 SDK 전환

직접 만든 API 호출을 걷어내고 공식 SDK로 옮겼습니다. 제출 로직을 AppInTossBridge 한 곳에 가두어, 게임 코드가 SDK 타입을 참조하지 않게 했습니다. 이후 SDK 버전이 바뀌어도 수정 범위가 이 파일 하나로 제한됩니다.

Unity 6000.0.31f1 → 6000.3.2f1 마이그레이션

SDK 요구 버전에 맞추기 위한 엔진 업그레이드였습니다. 함께 남아 있던 구형 WebGL 빌드 프로파일과 자체 토스 API 코드를 정리해, 빌드 경로를 하나로 통일했습니다.

노트·파티클 반복 생성으로 인한 프레임 튐

최종 정리 단계에서 오브젝트 풀을 도입해 Instantiate/Destroy를 재사용으로 바꿨습니다. 같은 시기에 Debug.Log를 전부 GameLogger로 교체해 릴리즈 빌드의 로깅 비용도 함께 제거했습니다.

기술 스택

직접 작성한 코드에서 실제로 사용한 항목입니다. 굵게 표시된 것이 이 프로젝트의 핵심 기술입니다.
